# Agent instructions

The brief invites AI assistance and asks for the prompts used. This file is the
harness that was in place before the first prompt; `CONVENTIONS.md` is the coding
standard it enforces. **Read `CONVENTIONS.md` first — it governs every change.**

## What this is

One HTTP endpoint and one screen. Four required operations: add, subtract,
multiply, divide. Three the brief marks optional — exponentiation, square root,
percentage — which land almost free once the contract holds, because they only
add rows to the test table and they are why `negative_sqrt` and
`result_not_finite` exist. Ship them after coverage, not before.

*Correctness, clarity and maintainability over extra features* — the way to fail
this is to decorate it. Extra features means history, chained operations, a
design system: not the operations the brief itself names.

## The API contract (frozen — changing it changes both sides and both test suites)

```
POST /api/v1/calculate
```

Request — `a` and `b` decode as `*float64`, never `float64`: with a plain
`float64`, an **absent** field and a **zero** field both arrive as `0`.
`{"op":"divide","a":10}` must fail with a missing field, not divide by zero.

```json
{ "op": "divide", "a": 10, "b": 4 }
```

Success (200) echoes the input, so a log line is self-contained:

```json
{ "op": "divide", "a": 10, "b": 4, "result": 2.5 }
```

Error (400) — one shape for every error. Never a 500 for bad input:

```json
{ "error": { "code": "division_by_zero", "message": "cannot divide by zero" } }
```

| `code` | When | HTTP |
|---|---|---|
| `invalid_json` | body is not valid JSON | 400 |
| `missing_field` | `op`, `a` or `b` missing | 400 |
| `unknown_operation` | `op` not in the list | 400 |
| `division_by_zero` | `b == 0` on `divide` | 400 |
| `negative_sqrt` | `a < 0` on `sqrt` | 400 |
| `result_not_finite` | result is `±Inf` or `NaN` | 400 |
| — | method other than `POST` | 405 |

`code` is for the machine, `message` for the person. The API does **not** round:
`0.1 + 0.2` returns `0.30000000000000004`. Formatting is the client's job.

## Frontend shape

Vite + React + TypeScript, `npm` (not pnpm: the reviewer clones and runs).
No router, no state manager, no component library. The API call returns a
discriminated union, it does not throw — that forces the component to handle the
error case in order to compile, the same reason Go returns `(value, error)`.
Error text comes from a `Record<Code, string>` map with a mandatory fallback.
Display formatting: `Intl.NumberFormat` with `maximumFractionDigits: 10`.

**The client does not validate division by zero on purpose.** It validates shape
only (empty field, non-numeric text). Domain rules are the server's, and a test
sends `{"op":"divide","a":10,"b":0}` and asserts the UI shows the server's
message.

## Same-origin, no CORS

Dev: Vite proxy `/api` → `localhost:8080`. Docker: nginx proxies `/api/` to the
backend service. The Go server never needs CORS headers, because in the shipped
topology the API and the page share an origin.

## Deliverables beyond the code

**The README's required sections are enumerated in the brief.** They go in as
literal headings, so a reviewer working down a checklist finds them without
reading the whole file:

1. Setup instructions
2. How to run the frontend and backend
3. Examples of API calls
4. Design decisions or assumptions

"…or assumptions" is an explicit invitation: the rounding contract, absent field
versus zero field, and `float64` precision are asked-for deliverables, not
colour. The single endpoint is justified here too — the brief says "expose
endpoints" in the plural, and an unexplained single route is the one place a
reviewer can read this as not meeting the requirement.

Also: `PROMPTS.md` (the narrative — what was asked, what was rejected and why,
including at least one prompt that went wrong), `PROMPTS.raw.md` (generated by
`extract-prompts.py`, read line by line before committing), and coverage output
from both sides.
